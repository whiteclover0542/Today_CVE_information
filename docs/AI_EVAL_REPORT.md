# 오늘의 CVE — AI 품질 평가 리포트

> 2026-09-04 기준. 진행 상태는 [`docs/AI_EVAL_PROGRESS.md`](AI_EVAL_PROGRESS.md), 도구 사용법은 [`scripts/eval/README.md`](../scripts/eval/README.md) 참고. 분류는 자동화 스크립트, 생성·브리핑·calibration은 독립된 새 Claude Code 세션의 직접 채점(`scripts/eval/CLAUDE_JUDGE_GUIDE.md` 지침, 원본 `scripts/eval/reports/claude-judge-*.json`) 결과다.

## 1. 개요

이 프로젝트(오늘의 CVE)는 NVD가 매일 새로 등록하는 CVE를 모아 심각도·유형별로 정리해 보여주는 정적 대시보드다. 이 중 LLM(Gemini)이 관여하는 지점은 셋뿐이고, 나머지(NVD 데이터 수집·CWE 집계·CVSS 해석)는 전부 규칙 기반이라 평가 대상에서 제외했다(위조 여지가 없음).

모델을 직접 재학습하는 대신, **각 LLM 호출의 출력물을 독립된 평가 방식으로 채점**하는 방식을 택했다. 분류는 NVD 공식 CWE로 만든 정답과 대조하고, 번역·해설·브리핑은 정답 문장이 없는 열린 텍스트라 G-Eval(별도 심사 모델이 체크리스트를 따라 1~5점을 매기는 방식)로 채점한다. 심사 모델 자체가 신뢰할 만한지도 별도로 검증한다(calibration).

```
NVD 신규 CVE 등록
        │
        ▼
   fetch-daily-count.mjs (배치)
        │
        ├─ 유형 태그(규칙 → '기타'만 LLM 재분류)    ──► (검문소 A) CWE 기반 골든셋 대조      → 분류 정확도 · F1
        ├─ 번역·해설(제목/요약/해석/원인/방지법)     ──► (검문소 B) G-Eval(Claude 독립 세션 심사)  → faithfulness · 번역정확도 · groundedCause · 자연스러움
        ├─ 오늘의 브리핑(1~3문장 요약)               ──► (검문소 C) G-Eval(Claude 독립 세션 심사)  → 무결성(위조 없음) · 관련성 · 자연스러움
        │                                              (검문소 D) calibration(good/bad 대조) → 검문소 B·C 심사 자체의 신뢰도
        ▼
   data/history.json → index.html (사용자 화면)
```

**왜 분류와 생성을 다르게 재는가**: 분류는 정해진 카테고리 중 하나를 고르는 닫힌 문제라 정답이 있다. 번역·해설·브리핑은 정답 문장이 없는 열린 텍스트라, 이 프로젝트가 가장 중시하는 "지어내지 않는다" 원칙을 기준으로 G-Eval이 채점한다.

## 2. 평가 대상 모델 인벤토리

| 기능 | 모델 | 역할 |
| --- | --- | --- |
| 유형(카테고리) 재분류 | `gemini-3.5-flash-lite` (무료 티어) | 규칙 매칭에서 '기타'로 빠진 CVE만 닫힌 목록 중 하나로 재분류 |
| 번역·해설 생성 | `gemini-3.5-flash-lite` (무료 티어) | 대표 CVE의 제목·한국어 요약·해석·발생 원인·방지법을 한 번의 호출로 생성 |
| 오늘의 브리핑 생성 | `gemini-3.5-flash-lite` (무료 티어) | 그날 집계 수치만 근거로 1~3문장 브리핑 생성(신규 기능, 아직 운영 미배포) |
| G-Eval 심사(Judge) | Claude(Sonnet 5), 독립된 새 Claude Code 세션 | 위 생성 결과물의 품질을 API 호출 없이 직접 읽고 채점 |

> 심사 모델은 세 단계를 거쳐 정착했다: ① pro 등급 Gemini(운영보다 무거운 모델) → 무료 티어 할당량이 0이라 접근 자체 불가. ② `gemini-3.5-flash` → 일일 할당량이 20건뿐이라 20건×4기준 채점 중 20콜만 성공하고 나머지는 429로 조용히 실패(표본 부족으로 무효 처리). ③ 결국 같은 제공사(Google) 모델이 자기 계열 출력을 채점하는 자기 편향 우려까지 겹쳐, **완전히 다른 제공사·모델인 Claude가 별도의 새 세션에서 직접 추론으로 채점**하는 방식으로 전환 — API 쿼터 문제 자체가 사라지고 자기 편향도 구조적으로 없앤다. 지침서는 [`scripts/eval/CLAUDE_JUDGE_GUIDE.md`](../scripts/eval/CLAUDE_JUDGE_GUIDE.md).

> ~~최초 정의는 "4개 기준을 통째로 평균 낸 bad 점수"였다~~ — 실제로 돌려보니 이 정의가 틀렸다는 게 드러나 수정했다. `calibration.json`의 bad 3건은 각각 **정확히 한 기준만** 오염시키도록 설계돼 있어서(예: 오역 사례는 translationAccuracy만 나쁘고 groundedCause는 정상), 4개 기준을 뭉뚱그려 평균 내면 오염 안 된 기준들이 점수를 희석시켜 "판별에 실패한 것처럼" 보이는 착시가 생긴다. calibration의 진짜 목적(심사가 결함을 정확히 짚어내는가)에 맞게 "그 사례가 노리는 기준"만 비교하도록 목표를 바꿨다. 자세한 경위는 §6-4 참고.

## 6. 항목별 해석

### 6-1. 분류 — 1차 평가에서 찾은 원인을 고쳐 목표 전부 통과

1차 평가(§7-1 원본 오분류 18건)에서 가장 큰 원인은 **`CATEGORY_RULES` 배열 순서**였다: `rce`/`auth-bypass`/`priv-esc`/`access-control`/`dos`처럼 "결과·전제조건"을 나타내는 규칙이 `sqli`/`xss`/`buffer-overflow`/`ssrf`처럼 "실제 취약점 유형"을 나타내는 규칙보다 먼저 검사되고 있어서, "SQL 인젝션인데 unauthenticated attacker라는 문구도 있다"는 이유로 `auth-bypass`에 잘못 걸리는 식의 오분류가 반복됐다. 이 다섯 개 규칙을 배열 맨 뒤로 옮기고, LLM 재분류 프롬프트에 idor·ssrf 전형적 패턴 힌트와 "결과가 아니라 메커니즘 기준으로 분류하라"는 지침을 추가한 뒤 재측정했다.

| 지표 | 개선 전 | 개선 후 | 비고 |
| --- | --- | --- | --- |
| Accuracy(전체) | 0.61 | **0.76** | 목표(0.70) 최초 통과 |
| Macro-F1(전체) | 0.77 | **0.87** | |
| Accuracy('기타' 단계만) | 0.61 | **0.78** | |
| Macro-F1('기타' 단계만) | 0.83 | **0.93** | |
| 규칙 매칭만(LLM 없이)의 accuracy | 0.41 | **0.50** | 순서만 바꿔도 이만큼 개선 — LLM과 무관한 순수 규칙 효과 |
| 오분류 건수 | 18건 | **11건** | |

규칙 재배치만으로 규칙 단계 자체의 정확도가 0.41→0.50으로 오른 것에서 보듯, 이 문제는 LLM보다 순수 규칙 설계 문제였다. 남은 오분류 11건 중 눈에 띄는 두 건은 프롬프트 힌트로도 못 고쳤다: `CVE-2026-85214`(idor)는 설명 마지막에 "cause denial of service"가 뚜렷하게 명시돼 있어 idor 대신 `dos`로, `CVE-2026-85180`(ssrf)은 "unauthenticated attackers" 문구가 여전히 `auth-bypass`로 이끄는 것으로 보인다 — 둘 다 한 문장에 여러 신호가 경쟁하는 근본적으로 애매한 케이스라, 프롬프트를 더 다듬기보다는 이 정도 잔차는 감수하는 쪽이 합리적으로 보인다.

### 6-2. 생성 품질 — 1차에서 찾은 원인(groundedCause 누락)을 고쳐 2차에서 5.00 확인

**1차**(개선 전, 골든셋 20건): faithfulness 4.90 · translationAccuracy 4.90 · groundedCause 4.65 · koreanFluency 4.90 — 네 기준 모두 목표(≥4.0)는 통과했지만, groundedCause가 가장 낮았다. 원인은 위조가 아니라 **누락**: `CVE-2026-78408`·`CVE-2026-85183`은 CWE 근거("파일 핸들 미해제", "WebSocket Origin 검증 누락")가 구체적으로 주어졌는데도 `cause` 필드가 빈 채로 나와 2점을 받았다.

프롬프트에 "CWE 근거가 주어지면 반드시 채워라"는 지시를 추가하고, 골든셋을 새 프롬프트로 재생성한 뒤 **2차 채점**을 했다: faithfulness 5.00 · translationAccuracy 4.95 · groundedCause **5.00**(+0.35) · koreanFluency 4.85. 두 케이스 모두 실제로 해당 CWE 힌트를 반영해 `cause`가 채워져 있음을 확인했다 — **수정이 의도대로 작동했다.**

koreanFluency는 4.90→4.85로 근소 하락했는데, `CVE-2026-18058`의 "없아서"(→"없어서") 오타 1건과 `CVE-2026-84841`의 어색한 이중 피동 구문("코드를 영향받게 하며") 1건 때문이다(§7-4·7-5). 1차에서 발견됐던 `CVE-2026-84841`의 "security flaw"→"보안 유출" 개념 오역은 2차에서 "보안 허점"으로 정정돼 사라졌다 — 다만 같은 문장의 다른 부분(어순)은 여전히 어색해 완전히 해결되지는 않았다.

### 6-3. 브리핑 품질 — 조사 오용(1차 원인)을 고쳐 2차에서 목표 재확인

**1차**: noFabrication 5.00 · relevance 5.00 · koreanFluency 4.00(목표 경계선) — "벤더별으로는"·"유형별으로는" 같은 조사 오용과 `BRIEF-QUIET`의 꼬인 문장이 원인이었다.

프롬프트에 "-별로/-별으로" 구분 규칙과 null 케이스 문구를 그대로 쓰라는 지시를 추가한 뒤 **2차 채점**: noFabrication 5.00 · relevance **4.75**(-0.25) · koreanFluency **5.00**(+1.00). 조사 오용과 꼬인 문장은 지침에 명시된 정확한 표현으로 교체돼 완전히 사라졌다 — **koreanFluency 수정이 확실히 반영됐다.**

relevance가 5.00→4.75로 소폭 내려간 건, `BRIEF-CWE-SPIKE`가 심각·높음 건수만 언급하고 중간·낮음은 "등"으로 생략해 심각도 분포 서술이 다소 불완전하다고 2차 심사가 판단했기 때문이다(§7-6) — 실제 회귀인지 이번 채점의 미세한 엄격도 차이인지는 표본 하나로는 단정하기 어렵고, 목표(≥4.0)는 여전히 넉넉히 통과한다.

### 6-4. 심사 자체 신뢰도(calibration) — 목표 재정의 후 명확히 통과

최초 목표("4개 기준 평균, bad ≤3.0")로 계산하면 bad 평균이 3.67로 미달처럼 보였는데, 원인을 보니 **목표 정의 자체가 잘못됐던 것**이었다. `calibration.json`의 bad 3건은 각각 결함을 **정확히 하나씩만** 심어뒀다(오역/날조된 사건/근거 없는 원인) — 그래서 4개 기준을 뭉뚱그려 평균 내면 오염 안 된 기준 3개가 오염된 기준 1개의 신호를 희석시킨다.

실제로 "그 사례가 노리는 기준"만 떼어보면 세 사례 모두 **정확히 1점**을 받았다: 오역 사례(`CALIB-BAD-MISTRANSLATION`, "Submariner"→"잠수함")는 translationAccuracy=1, 날조 사례(`CALIB-BAD-FABRICATED-INCIDENT`, 없는 해킹 그룹·공격 사례)는 faithfulness=1, 근거 없는 원인 사례(`CALIB-BAD-UNGROUNDED-CAUSE`, CWE-787과 무관한 서사)는 groundedCause=1 — good 사례(전 기준 5.00)와의 격차가 4.0에 달한다. 더 중요한 건 **오염 안 된 나머지 기준은 그대로 높게 유지됐다는 점**(예: 오역 사례도 cause 자체는 정상이라 groundedCause 5점) — 심사가 "bad니까 전부 감점"하는 식으로 뭉뚱그리지 않고, 실제 텍스트를 보고 기준별로 독립적으로 판단했다는 뜻이다. §4-4 목표를 이 "타겟 기준" 기준으로 다시 정의했고, 이 기준으로는 명확히 통과다.

## 7. 사례 분석

### 7-1. 분류 오분류 — 개선 전(18건) → 개선 후(11건)

개선 전 1차 평가에서 발견한 패턴(규칙 순서 문제로 `idor`/`buffer-overflow`/`xss`/`sqli` 등이 `rce`/`auth-bypass`/`priv-esc`에 밀리는 것, CATEGORY_RULES 재배치로 대부분 해결)은 §6-1의 Before→After 표로 정리했다. 개선 후 남은 11건 중 아직 뚜렷한 패턴 두 가지만 남았다:

| 패턴 | 해당 사례 | 해석 |
| --- | --- | --- |
| `buffer-overflow` 근거인데 `deserialization`/`buffer-overflow`(정수 오버플로우 쪽)로 혼동 | CVE-2026-85455(CWE-125→deserialization), 85438·85436(CWE-190/191→buffer-overflow) | 정수 오버플로우가 버퍼 오버플로우로 이어지는 서술이라 인접 카테고리끼리 혼동 — 두 유형이 실제로 밀접해 완전히 갈라내기 어려운 경계 사례 |
| 한 문장에 여러 신호가 경쟁하는 근본적 애매함 | CVE-2026-85214(idor인데 "denial of service"가 문미에 명시), CVE-2026-85180(ssrf인데 "unauthenticated attackers" 문구가 강함) | §6-1에서 이미 다룸 — 프롬프트로 완전히 없애기보다 잔차로 감수 |
| "정답이 원래 other" 사례를 여전히 다른 유형으로 무리하게 분류 | CVE-2026-85183·80098·85394 | "애매하면 other 유지" 지침을 더 강조해도 이 3건은 여전히 남음 — 표본이 작아(46건) 이 패턴이 실제로 개선 여지가 있는지, 아니면 무료 티어 모델의 근본 한계인지는 표본을 늘려 재확인 필요 |

### 7-2. 생성 품질 — koreanFluency 저하 사례(CVE-2026-4703) → 골든셋 결함으로 정정

처음엔 이 케이스를 "NVD 원문이 문장 중간에서 잘려 직역 비문이 생긴 사례"로 분석했으나, 다시 확인해보니 **이 케이스 자체가 골든셋 빌더 버그로 잘못 포함된 것**이었다. `CVE-2026-4703`은 2026-08-23(가장 오래된 기록)에 생성된 것으로, `title`/`interpretation`/`cause`/`mitigation`/`cwe` 필드가 애초에 스키마에 없던 구버전 기록이다. `build-generation-golden-set.mjs`가 `summaryEn`/`summaryKo` 존재 여부만 확인하고 나머지 필드 존재를 확인하지 않아, "번역·해설을 시도했지만 필드가 비었다"가 아니라 "애초에 시도 자체가 없었던 옛 기록"을 마치 생성 실패 사례처럼 채점하게 됐다. 필터를 보강해(`title`/`interpretation`/`cause`/`mitigation`이 모두 존재하고 `cwe`가 비어있지 않은 것만 포함) 골든셋을 다시 만들었고, 이 케이스는 더 이상 포함되지 않는다.

이 사례가 남기는 진짜 교훈은 번역 품질이 아니라 **골든셋 자동 생성 로직에도 검증이 필요하다**는 것이다.

### 7-3. 생성 품질 — 긍정적 발견: Submariner 오역 재발 없음

새로 만든 골든셋(52건 후보 중 20건)에 우연히 과거 이슈였던 "Submariner"(쿠버네티스 네트워크 플러그인) 관련 CVE가 포함됐다(`CVE-2026-66786`). 이 프로젝트는 예전에 MyMemory 번역 API를 쓰던 시절 "Submariner"를 "잠수함"으로 오역한 전례가 있었는데, 지금의 Gemini 기반 번역 결과는 `summaryKo`에 "Submariner"를 고유명사 그대로 유지했고, Claude 심사도 translationAccuracy 5점으로 확인했다 — **번역 방식을 MyMemory→Gemini로 바꾼 개선이 실제로 이 문제를 해결했다는 정황 증거**다. calibration 골든셋의 good 사례(`CALIB-GOOD-2`, 별도로 손으로 만든 Submariner 시나리오)에서도 같은 결과가 나와, 표본 1건이 아니라 최소 2건에서 일관되게 확인됐다.

### 7-4. 생성 품질 — CWE 근거가 있는데도 원인을 비운 사례 2건 → ✅ 수정 확인

`CVE-2026-78408`(CWE-775, 파일 핸들 미해제)과 `CVE-2026-85183`(CWE-1385, WebSocket Origin 검증 누락)은 1차 채점 때 CWE 근거가 구체적으로 주어졌는데도 `cause` 필드가 빈 채로 생성돼 groundedCause 2점을 받았다. "근거 없으면 지어내지 말고 비워두라"는 프롬프트 지시를 지나치게 보수적으로 따른 결과로 보였다.

`explainHighlightWithLlm()` 프롬프트에 "CWE 근거가 주어졌다면 반드시 그 근거를 원인으로 채워라(빈 문자열 금지)"를 명시적으로 추가하고 골든셋을 재생성한 뒤 재채점한 결과, 두 케이스 모두 해당 CWE 힌트가 그대로 `cause`에 반영돼 5점을 받았다 — **수정이 실제로 작동함을 확인.**

### 7-5. 생성 품질 — 오역+비문 복합 사례(CVE-2026-84841) → 오역은 해결, 어순 문제는 잔존

1차: "security flaw"를 "보안 결함"이 아니라 "보안 유출"로 오역했다(결함↔유출은 서로 다른 개념) — translationAccuracy 3점. 같은 문장에 조사가 빠진 비문("이 취약점은 알 수 없는 코드를 영향 주며")도 함께 나타나 koreanFluency도 3점을 받았다.

골든셋 재생성 후 2차 채점: "보안 유출"이 "보안 허점"으로 정정돼 **개념 오역은 사라졌다**(translationAccuracy 4점으로 개선). 다만 같은 문장에 남아있던 다른 어순 문제("이 취약점은 알 수 없는 코드를 영향받게 하며" — 주어-목적어 관계가 꼬인 이중 피동/사동 표현)는 그대로라 koreanFluency는 여전히 3점이다. 심각한 오역은 고쳤지만 해당 문장 자체의 자연스러움은 아직 다듬을 여지가 있다 — 표본 1건짜리 잔여 이슈라 추가 프롬프트 튜닝보다는 관찰만 해도 될 수준으로 판단.

### 7-6. 브리핑 품질 — 조사(助詞) 오용 반복 패턴 → ✅ 수정 확인, relevance는 근소 하락

1차: `BRIEF-CWE-SPIKE`("벤더별으로는")와 `BRIEF-CRITICAL-HEAVY`("유형별으로는")에서 표준적이지 않은 조사 사용이 반복됐고, `BRIEF-QUIET`은 `topCwe`가 null일 때 나온 문장의 주어-수식 관계가 꼬여 3점을 받았다.

프롬프트에 "-별로/-별으로" 구분 규칙과 null 케이스 문구를 그대로 쓰라는 지시를 추가한 뒤 재생성·재채점한 결과, 4건 모두 조사 오용과 꼬인 문장이 사라져 koreanFluency 만점(5.00)을 받았다 — **수정이 실제로 작동함을 확인.** 다만 relevance가 `BRIEF-CWE-SPIKE`에서 4점으로 소폭 내려갔는데(심각·높음 건수만 언급하고 중간·낮음을 "등"으로 생략), 이건 조사 수정과 무관한 별개 관찰로 회귀인지 채점 편차인지는 추가 표본이 필요하다.

### 7-7. 생성 품질 — 2차 채점에서 새로 발견된 경미한 잔여 결함

`CVE-2026-18058`의 `cause` 필드에 "없아서"(→"없어서") 오타가 하나 있었다 — 사실 왜곡과는 무관한 단순 오타. koreanFluency 4.90→4.85로 근소 하락한 두 원인(이 오타 + §7-5의 어순 문제) 중 하나다. 표본 20건 중 1건이라 심각하게 볼 정도는 아니다.

## 9. 종합 의견

- **분류**: 1차 평가에서 찾은 근본 원인(`CATEGORY_RULES` 순서 문제)을 고치고 LLM 프롬프트에 idor·ssrf 힌트를 보강해 재측정한 결과, accuracy 0.61→0.76·macro-F1 0.77→0.87로 **모든 목표를 통과**했다(§6-1). 순수 규칙 매칭만으로도 0.41→0.50 개선된 것에서 보듯, 애초 문제의 상당 부분은 LLM이 아니라 규칙 설계였다. 남은 11건은 카테고리 경계가 근본적으로 애매한 사례들이라 잔차로 감수한다.
- **생성 품질**: 1차에서 가장 낮았던 groundedCause(4.65, CWE 근거 있는데 cause 비움)를 프롬프트로 고치고 2차 채점에서 **5.00으로 개선 확인**(§6-2). translationAccuracy·faithfulness도 만점권 유지. koreanFluency만 4.90→4.85로 근소 하락했는데 오타 1건·어순 문제 1건뿐이라 사실상 잡음 수준이다. 가는 길에 golden set 자체 결함(구버전 스키마 기록 혼입, §7-2)도 하나 발견해 고쳤다.
- **브리핑 품질**: 1차의 유일한 흠이었던 koreanFluency(4.00, 조사 오용)를 프롬프트로 고치고 2차 채점에서 **5.00으로 개선 확인**(§6-3). relevance가 5.00→4.75로 소폭 내려간 건 조사 수정과 무관한 별개 관찰이라 회귀 여부는 추가 표본이 필요하다.
- **심사 자체 신뢰도(calibration)**: 처음 정의한 목표("4개 기준 평균")로는 미달처럼 보였지만, 실제로는 **목표 정의 자체가 틀렸던 것**임을 확인하고 "타겟 기준" 기준으로 바로잡았다(§6-4) — 이 기준으로는 bad 3건 모두 정확히 노린 기준에서 1점을 받아 1·2차 모두 명확히 통과(격차 4.0, 동일). 이 과정 자체가 "평가 프레임워크도 검증이 필요하다"는 걸 보여준 사례다.
- **심사 방식 전환**: Gemini 자기 채점(pro 등급 접근 불가 → non-lite flash 할당량 20건/일 소진으로 이중 실패)을 폐기하고, 완전히 다른 제공사·모델인 Claude가 별도의 새 세션에서 API 호출 없이 직접 채점하는 방식(`scripts/eval/CLAUDE_JUDGE_GUIDE.md`)으로 전환해 쿼터 문제와 자기 편향 우려를 동시에 해소했다 — 같은 방식으로 1차(개선 전)·2차(개선 후) 채점을 각각 수행해 프롬프트 수정의 효과를 직접 비교할 수 있었다.
- **운영 코드에 곁들여 고친 것**: 생성·브리핑 API 호출에 재시도 로직을 추가하는 과정에서, 기존 재시도 대기시간(고정 2초)이 실제 분당 요청 한도 초과 시 서버가 요구하는 대기시간(15~20초)보다 훨씬 짧아 재시도해도 다시 실패하는 버그를 발견해 함께 고쳤다(서버가 알려준 시간만큼 정확히 대기하도록 수정, §8).
- 종합적으로 이 프로젝트의 AI 파이프라인(분류/번역·해설/브리핑)은 "지어내지 않는다"는 핵심 원칙을 이번 표본에서 잘 지켰고, 남은 과제는 위조보다는 **누락·오역·조사 오용 같은 다듬기 수준의 결함**이다. 이 문서는 한 번의 완성본이 아니라 매 프롬프트/로직 변경마다 다시 돌려 회귀를 감지하는 용도로 계속 갱신되어야 한다.
